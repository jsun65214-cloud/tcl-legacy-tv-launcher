# 我们怎样让这台 Android 4.2.1 电视更流畅

这次改造有两部分：用原生轻量首页改善日常入口，再通过实际测量处理拖慢电视的应用。下面记录的是一台 TCL MS901 的结果，时间为 2026-10-25。

## 先找问题，不按应用数量猜

用户反馈桌面、菜单和遥控器响应都慢。我们连续采了五次 CPU，并查看进程、内存、服务、存储和错误日志。

| 检查项 | 发现 |
| --- | --- |
| 处理器 | 双核 ARMv7 / Cortex-A9，性能余量有限 |
| Android 可见总内存 | 约 861MiB |
| 安装包数量 | 106 个，包含系统组件 |
| 数据分区 | 共约 4.84GB，剩余约 3.23GB |
| 卡顿期间 | ATET游戏大厅连续占整机约 46%～49% CPU，整机约 55%～58% |
| 同期系统 CPU 统计 | 游戏大厅约占一个核心的 95%，两种统计口径相符 |

存储空间仍多；首轮采样中没有直接回收、kswapd 扫描或 allocstall 持续增加的迹象。内存小是设备的长期限制，但当时最明确的问题是游戏大厅的高 CPU。

Android 会使用缓存，不能只用 MemFree 判定内存耗尽。PSS、RSS、VSS 也不是同一个指标。参考 [Android dumpsys 文档](https://developer.android.com/tools/dumpsys) 与[内存管理说明](https://developer.android.com/topic/performance/memory-management)。

## 对照：返回桌面后发生了什么

最初高占用时，游戏大厅的设备识别页面处于前台；不能描述为它一直在后台偷偷吃 CPU。日志里有多次连接超时、网络不可达和域名解析失败，但没有抓到高 CPU 时的线程栈，不能断言具体哪一段重试代码导致占用。

用户返回简洁桌面后明确反馈明显流畅。复测整机 CPU 约 6%～9%，游戏大厅仍驻留，却降到接近 0%。这一步还没有卸载任何应用，说明“把后台全杀掉”不是诊断的起点。

## 按实际需求移除三款应用

在用户明确要求后，处理了：

| 应用 | 包名 | 本机采用的方式 |
| --- | --- | --- |
| ATET游戏大厅 | `com.sxhl.tcltvmarket` | 系统预装，移出应用扫描目录，保留原包 |
| 云视听 | `com.voole.epg` | 系统预装，移出应用扫描目录，保留原包 |
| 鲜时光 | `com.ixigua.android.tv.wasu` | 普通安装包，标准卸载 |

“云视听”在这台电视上是优朋的应用，**不是 NewTV极光/腾讯视频**。我们先核对显示名称、包名和安装来源，腾讯视频保留。

两个系统包的普通卸载和停用都被该固件拒绝。用户另行授权后，电视自带的 `adb root` 可用；没有使用漏洞或刷机。原包移到非扫描目录，验证安装清单从 106 减为 103，再将系统分区恢复只读。这是高级可选流程，安装桌面与只读诊断不需要这样做。细节在[机型操作目录](../profiles/tcl-ms901/README.md)。

## 真正检查“退出后留了什么”

我们打开应用，按返回键，在退出对话框里选择退出；立即及延迟超过约 30 秒查看进程和服务。没有以强制停止替代正常退出。

| 应用 | 结果 | 是否处理 |
| --- | --- | --- |
| 腾讯视频 | Java 主进程和服务消失，留下 `libvideocore.so` 独立原生辅助进程；RSS 约 228KB，CPU 接近 0% | 保留，负担很小 |
| QQ音乐 | 未检测到其 Java 进程或运行服务 | 无需处理 |
| 已移除的云视听 | 原来的 `videodaemon`、`vooleauthd` 仍运行；前者采样约占整机 2% CPU | 先核对 UID 与可执行文件所属，再停止这两个目标残留 |

`ps` 里存在进程不一定意味着它在持续消耗 CPU。原生辅助进程也可能不出现在常规的 Android 服务列表。需要结合包名、UID、可执行文件、CPU 和内存判断。系统通常按组件重要性与内存需求回收进程，见 [Android 进程生命周期](https://developer.android.com/guide/components/activities/process-lifecycle)。这里未采用现代 Android 的冻结器等特性解释旧版系统。

其他原厂游戏中心、语音和投屏服务保留，没有因为名字像“后台”就扩大删除范围。这次只测试了两款保留应用的正常退出，不代表全部应用及播放、下载、投屏场景都已经验证。

## 最终结果与仍可改进的地方

处理目标应用和残留后，桌面三次采样整机 CPU 约为 6%、5%、4%。用户确认 HDMI1 节目画面、声音、回主页及背景声音停止都正常。

轻量首页本次 PSS 约 18.3MiB，原厂首页约 43.6MiB；原厂首页仍保留在系统中，因此不是装新桌面就自动释放全部旧桌面占用。

本项目为解决 HDMI 背景声音而同步调用的信源切换，进入首页时有约 3 秒短暂等待；这是独立的实现限制，还可以继续优化。本次没有关闭开机广告，没有强行修改系统调度参数，也没有自动重启电视。温度和 CPU 频率标准节点没有提供数据，不能据此排除一切硬件问题。

## 复现诊断方法

```powershell
.\scripts\Inspect.ps1 -Serial "<电视IP>:5555"
```

先在卡顿场景运行一次，再正常退出应用、回到桌面运行一次，比较 `cpu-samples.txt`、`processes.txt`、`services.txt`、`memory-by-process.txt`。采 CPU 时不同时复制大文件或反复截图，避免把调试传输的开销当成应用负载。

如要检查具体 App，先记下它的包名，正常退出后再查看：

```powershell
adb -s "<电视IP>:5555" shell ps
adb -s "<电视IP>:5555" shell dumpsys activity services "<包名>"
adb -s "<电视IP>:5555" shell dumpsys meminfo "<包名>"
```

原始诊断文件可能含设备与账号信息，默认留在 `.local/`；反馈问题时提供必要的脱敏摘要。
